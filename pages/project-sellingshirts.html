Overview

โครงงานคืออะไร

โปรเจกต์งานวิชาที่อาจารย์ให้ดูเว็บขายเสื้อของอาจารย์เป็นตัวอย่างแนวคิด (ไม่ใช่ clone โค้ด) แล้วให้นักศึกษาออกแบบและสร้างขึ้นเองทั้งหมด เพื่อให้อาจารย์ประเมินคะแนนด้าน design และ UI/UX ระบบจำลองร้านขายเสื้อขนาดเล็ก-กลาง ที่ต้องจัดการสต๊อกตามไซซ์/สี ยืนยันการชำระเงินด้วยสลิปแบบ manual (ไม่ผูก payment gateway) และมีสิทธิ์ผู้ใช้สองระดับคือลูกค้ากับแอดมิน

🎯

แก้ปัญหาร้านเสื้อขนาดเล็กที่รับออเดอร์ผ่านแชท/โพสต์ ตามสต๊อกและสถานะจ่ายเงินด้วยมือ สับสนและตกหล่นง่าย

🧾

ระบบเก็บ state ของออเดอร์ตั้งแต่รอชำระจนถึงจัดส่งเสร็จ ให้แอดมินกดอนุมัติทีละสถานะแทนการนับสต๊อกด้วยมือ

Features

สิ่งที่ระบบทำได้

🛍️

Product & Stock

จัดการสินค้าแยกตามไซซ์/สี พร้อมรูปสินค้าเก็บผ่าน Cloudinary

🧾

Order + Slip Upload

ลูกค้าสั่งซื้อและอัปโหลดสลิปโอนเงินเอง ไม่ต้องผูก payment gateway

✅

Admin Approval

แอดมินตรวจสลิปแล้วอนุมัติออเดอร์ทีละสถานะผ่าน dashboard

🔐

JWT + Google OAuth

ลูกค้าล็อกอินด้วยเบอร์โทรหรือ Google ก็ได้ auth ด้วย access + refresh token

🧑‍💼

Two-Tier Admin

แยก super admin กับ staff admin ล็อกอินคนละทางผ่าน /admin_login

📊

Admin Dashboard

ภาพรวมออเดอร์ สินค้า และผู้ใช้ทั้งหมดในหน้าเดียว

📜

Order History

ลูกค้าดูประวัติออเดอร์และสถานะย้อนหลังได้ทุกเมื่อ

🖼️

Cloudinary Storage

รูปสินค้าและสลิปโอนเงินเก็บเป็น URL บน Cloudinary ไม่เก็บไฟล์บนเซิร์ฟเวอร์

System Workflow

วงจรชีวิตของออเดอร์

  1. 1

    Pending Payment

    ลูกค้าสร้างออเดอร์ สถานะเริ่มต้นรอชำระเงิน

  2. 2

    Verifying Payment

    ลูกค้าอัปโหลดสลิปโอนเงินผ่านหน้า Orders

  3. 3

    Paid

    แอดมินตรวจสลิปแล้วอนุมัติ บันทึก approvedBy และ paidAt

  4. 4

    Shipping

    แอดมินอัปเดตสถานะเป็นกำลังจัดส่ง

  5. 5

    Completed

    ปิดวงจรออเดอร์เมื่อจัดส่งสำเร็จ

Challenges & Solutions

ปัญหาที่พบ กับวิธีแก้

ร้านเสื้อขนาดเล็กรับออเดอร์ผ่านแชท/โพสต์ ตามสต๊อกและสถานะจ่ายเงินด้วยมือ สับสนและตกหล่นง่าย

ให้ลูกค้าสั่งซื้อและอัปโหลดสลิปเองผ่านเว็บ ระบบเก็บ state ของออเดอร์ให้อัตโนมัติ

ไม่มี payment gateway ต้องยืนยันการชำระเงินด้วยสลิปแบบ manual

ลูกค้าอัปโหลดสลิปเข้า Cloudinary แอดมินตรวจแล้วกดอนุมัติทีละสถานะ พร้อมบันทึก approvedBy และ paidAt

เสี่ยงมีคนแก้สถานะออเดอร์ข้ามขั้นตอนตรง ๆ ใน DB

บังคับเปลี่ยนสถานะได้ทางเดียวผ่าน endpoint ของแอดมินเท่านั้น ห้ามแก้ field status ตรง ๆ

ราคาสินค้าคำนวณผิดถ้าคิดที่ frontend

ย้าย totalProductPrice + shippingCost = totalPrice ไปคำนวณที่ backend เท่านั้น
